The problem it solves

Management teams routinely compare this month against last month, which seasonality distorts badly — December always looks like a triumph next to November. Meanwhile overdue receivables sit unwatched, and nobody knows the real collection cycle.

What the dashboard does

  • Executive summary — revenue, gross margin, operating profit, overdue receivables and DSO, with month-over-month revenue plotted against the same month last year, so seasonality stops fooling the reading.
  • Sales analysis — a client-by-month heatmap that surfaces who is growing and who is quietly slipping, plus performance by salesperson and by city.
  • Receivables and expenses — overdue invoices ranked by client, receivables by status, and monthly spend by category. In most SMEs this page is where forgotten cash turns up.

How it was built

  • A single 18-month dataset drives every visual — nothing is a pasted image. Margin, operating profit, month-over-month and year-over-year variance, receivables ageing and DSO are all computed live on the page.
  • Cross-filtering across every visual: one click on a month drills the entire report
  • Shipped as one self-contained page — it opens in any browser, with no server and no licence behind it
Open the live dashboard

Systems integration · Client engagement

Rescuing an integration that had silently stopped working

An hourly automation moving issues from Jira into a Dataverse table had been reporting failed runs for weeks. Data had stopped flowing entirely, and the error the connector returned pointed at the wrong thing.

The apparent cause versus the real one

The connector reported that records could not be found, which read as a data problem. It was not. Records were looked up by a business key containing a colon — a value like jira:ADM-123 — and the colon broke the request URL. The service returned an HTML error page, which the connector then surfaced as "record not found". The update-by-alternate-key step had in fact never worked; it had been failing quietly since the integration was built.

The redesign

  • Look up by filter rather than by alternate key, so the value is encoded correctly regardless of the characters it contains
  • Update by internal identifier (the record GUID) once the row is located, which removes the fragile path entirely
  • Create only when the lookup returns empty, with the uniqueness constraint retained as a safety net rather than as the primary mechanism

Result

A verified clean run reconciling roughly 1,300 records with no duplicates, and the incremental window tightened from a year to two hours — which cut both the runtime and the risk of a backlog rebuilding unnoticed.

Odoo · Client engagement

Odoo ERP implementation and process automation

Led the Odoo implementation and digital transformation programme for a professional services firm, from requirements gathering through deployment and team adoption.

Scope of the work

  • Requirements and process mapping across departments — documenting how work actually ran before deciding what the system should enforce
  • Module configuration and custom development — tailored modules and reports for operational needs the standard configuration did not cover
  • API integrations connecting Odoo with external platforms, including electronic invoicing under local tax regulation — delivered alongside a licensed accounting firm that handles the certification and fiscal side
  • Management reporting layer — KPI and OKR definitions built on top of ERP data, so leadership read the same numbers the operation produced
  • Training and adoption — the part most implementations underinvest in, and the reason many of them fail

The approach that made it work

Configuration decisions were made against the accounting they produce, not only the process they automate. A purchasing flow that is elegant operationally but posts entries the finance team has to correct manually every month is not automation — it just moved the work.
